5. Source discovery and ingestion
5.1 Supported content detection
Do not select a parser using only a .xls/.xlsx extension. Sniff the content signature and parse strategy, because legacy `.xls` downloads may actually be HTML tables. Keep parser choice and detected media type in the source manifest.
Detected source format
 | Parser strategy
 | Handling
 | 
HTML table saved as .xls
 | Read small byte prefix; parse with pandas.read_html or a controlled HTML parser.
 | Store parser type; validate column names and row counts.
 | 
Native legacy XLS
 | Use xlrd-compatible parser where available.
 | Check sheet names, types and headers; preserve original bytes.
 | 
XLSX
 | Use openpyxl/pandas where appropriate.
 | Validate worksheet/schema.
 | 
CSV
 | Use pandas/read_csv with encoding/delimiter detection and explicit date parsing.
 | Report ambiguous formats instead of guessing silently.
 | 
PDF contract documents
 | Register/hash; optional text extraction for suggestions.
 | Human-reviewed contract master is authoritative; original PDF remains unchanged.
 | 
Unsupported/unknown
 | Do not try unsafe coercion.
 | Quarantine with reason and provide a data-quality report.
 | 

5.2 Source categories
Futures price source: rows explicitly classified as futures (e.g., FUTCOM) with a recognized target symbol, trade date, actual expiry and valid price fields.
Activity report: detail/summary reports containing traded lots and aggregate total value. Store separately from price bars; aggregate value divided by lots may be an activity-derived proxy, not an official settlement price.
Options/OPTFUT source: classify separately. Do not join into target futures series solely because the underlying symbol says GOLD.
Contract specification: store references and verified effective-dated metadata, including source document and reviewer/status.
Illustrative TypeScript data: stays in frontend fallback and is never ingested into verified market tables as genuine market data.
5.3 Ingestion workflow
Configured read-only source root        ↓Discover file + SHA-256 + byte size        ↓Sniff content / select parser        ↓Parse to source-specific raw rows        ↓Classify: futures / activity / options / specs / unknown        ↓Validate schema, dates, symbol, expiry, prices and activity        ↓Accepted rows ───────── Rejected/ambiguous rows      ↓                           ↓Staging + quality tag         Quarantine/report only      ↓Normalized tables + lineage      ↓Features / novelty / API
 | 
5.4 Import safety
Source roots are opened read-only; importer cannot output generated files to the source root.
At the start of import, compute a manifest with SHA-256 hashes. In tests, verify original hashes are unchanged after scan/import.
Use a database transaction for each file or bounded batch. Failed files should not leave partial normalized rows.
Make imports idempotent using source hash + row hash + natural keys; reimport should update status, not duplicate the same source row.
Use row-level reasons for quarantine; e.g. unsupported instrument, missing date, missing expiry, OHLC absent, invalid OHLC order, all-zero activity, unknown symbol, ambiguous quote basis.
Never fabricate missing OHLC values from totals or fill absent observations by forward/backward filling without an explicit analytical rule.

7.2 Pair identifiers and frontend compatibility
Backend canonical pairs are fixed, stable identifiers: GOLDM-GOLDTEN, GOLDM-GOLDGUINEA, GOLDM-GOLDPETAL, GOLDTEN-GOLDGUINEA, GOLDTEN-GOLDPETAL, GOLDGUINEA-GOLDPETAL. The current frontend has a legacy typo `REST-GOLDPETAL` for the last pair. Preserve the frontend source initially and translate that alias at the API adapter boundary; do not store the typo as canonical backend identity.
7.3 Specification versioning
Contract metadata must be effective-dated: `valid_from`, `valid_to`, `source_document_id`, `verification_status`, `trading_unit_grams`, `quote_grams`, `purity_per_mille`, and a `quote_rule`/`fine_grams_per_quote` rule as approved. The normalization service must use the specification valid on the observation date, not automatically apply current metadata to all history.
Normalization rule  Use a common comparable price only after verifying how the official contract price is quoted. For standard contracts where the quote price applies to a known gross quoted quantity, price per fine gram can be calculated as quote price divided by quote grams × purity fraction. If a contract has a special quotation/premium rule, encode that rule explicitly and test it; never assume a generic formula fits every contract.

8. Core analytics and novelty detection
8.1 Feature pipeline
Feature group
 | Initial features
 | Rules
 | 
Price relationship
 | Normalized value, pair spread %, price ratio, return difference.
 | Compute from compatible instrument/expiry/date mappings.
 | 
Robust statistics
 | Rolling median, MAD, robust modified z-score, IQR fallback.
 | Window only uses observations available by score timestamp.
 | 
Activity
 | Volume/lots, OI, pair ratios where records are comparable.
 | Aggregate activity reports are not market depth.
 | 
Expiry lifecycle
 | Days to expiry, expiry window, contract age.
 | Use actual contract expiry; do not splice near-month contracts silently.
 | 
Regime/context
 | Gold return, rolling volatility, regime label if justified.
 | Do not remove crisis data mechanically; account for common movement/regime.

8.2 Statistical baseline parity
First backend release should reproduce the existing `src/lib/anomalyScore.ts` behaviour so frontend and backend results can be compared. The existing implementation uses median, MAD, modified z = 0.6745 × (x − median) / scale, absolute threshold 3.5, score min(|z|/6, 1), an IQR/1.349 fallback when MAD is approximately zero, and a small scale floor as the final fallback. Preserve and test these rules before making improvements.
median = median(training_spreads)MAD = median(abs(x - median) for x in training_spreads)scale = MAD if MAD > epsilon else IQR / 1.349scale = scale if scale > epsilon else configured_floorrobust_z = 0.6745 * (new_spread - median) / scalescore = min(abs(robust_z) / 6, 1)is_anomaly = abs(robust_z) >= 3.5
 | 
8.3 Training/score contract
Calibration is specific to canonical contract pair and a declared feature/configuration version.
Calibration training window is explicit (start/end dates and cutoff timestamp); score-time observation and future observations are excluded.
Only observations marked eligible by data-quality and expiry/contract mapping rules can enter the training sample.
Mostly-normal training observations are expected, not guaranteed. Record training row IDs, quality filtering, count, median, scale, fallback type, threshold and algorithm version.
The baseline scores primarily one relative-spread feature; do not describe it as a multivariate Isolation Forest unless a different model is genuinely implemented.
Anomaly score is not a calibrated probability, not proof of mispricing, and not evidence of profitability.
Add Isolation Forest only as a separate model version after baseline tests, sufficient clean examples, and chronological evaluation exist.

12. Security, reliability and operations
Use environment variables for secrets and database URLs. Commit only .env.example placeholders.
Limit CORS to the configured frontend origin(s); do not enable wildcard credentialed CORS.
Keep ingestion/import/calibration/backtest-admin operations local or access-controlled; do not expose arbitrary filesystem paths to clients.
Resolve source file paths under the configured root and reject path traversal/symlinks escaping the root.
Enforce upload size limits, supported file types, parser timeouts and safe error messages.
Use structured logs with request IDs and import-run IDs. Do not log credentials.
Use database transactions, unique constraints and idempotent import keys.
Expose liveness and readiness checks separately. A running process with an unavailable DB should not report full readiness.
For first release, use Docker Compose for API + PostgreSQL if available; avoid adding Redis/Celery until workload demands it.

15. Definition of done
Backend has a documented install/run process and working health/readiness endpoints.
Database schema is migration-managed, not only created ad hoc.
Original frontend visual components/pages and source data files have not been destructively changed.
Every imported file is registered with SHA-256, detected format, source class, parser version and import result.
Input files are never changed; quarantine/export/log storage is outside the raw source root.
Options/activity/specification rows are not silently mixed into futures OHLC history.
Canonical contract IDs and all six canonical pair IDs are stable.
Normalizing and novelty-scoring calculations have independent unit tests and transparent explanations.
All market/derived API results carry provenance/data quality and algorithm version as applicable.
Existing frontend has local mode and preserves its visual design; API/hybrid mode is configurable.
Walk-forward validation uses chronologically separated training/test windows and reports costs/assumptions.
Data limitations and unverified metrics are documented in README and API/UI status messages.
