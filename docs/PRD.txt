1. Executive summary
MCX Gold Intelligence currently runs as a frontend-only React/TypeScript/Vite application with local TypeScript datasets and a browser-side median/MAD novelty-scoring baseline. The goal is to add a backend that provides centralized storage, source-data ingestion, normalization, pairwise relative-value features, anomaly scoring, signals and reproducible backtesting while keeping the existing UI visually unchanged.
Non-negotiable  Do not delete, rename, rewrite, reformat or move the existing frontend source tree or original market-data files. The backend is additive. Any frontend integration change must be limited to a thin data-access adapter and minimal call-site changes, with a working local-demo fallback.
 | 
2. Current-state baseline
The repository snapshot contains index.html, package.json, Vite/Tailwind/TypeScript configuration, src/App.tsx, reusable components, eight main page modules, local data modules and src/lib/anomalyScore.ts. The existing pages include Dashboard, Signals, Contracts, Comparison, Model Demo, Market Insights, Learn and Backtest & Events.
Existing local datasets include contracts.ts, marketSeries.ts, spreads.ts, noveltyTraining.ts, testObservations.ts, signals.ts, historicalEvents.ts, researchCards.ts and backtestScenarios.ts. These must remain available as a local mode during migration.
The supplied source-data folder contains contract PDFs and date-wise detail/summary reports, plus separate commodity-wise BhavCopy examples. Files with an .xls extension may be HTML tables rather than native Excel workbooks; the importer must detect content format instead of trusting the extension alone.
Known integration risk  The current frontend contains a legacy pair identifier REST-GOLDPETAL where the canonical pair is GOLDGUINEA-GOLDPETAL. The backend must use canonical identifiers and a compatibility adapter must preserve existing frontend behavior until a deliberate frontend fix is approved.
 | 
3. Product vision and goals
3.1 Product vision
Provide a reliable analytical service behind the current product that turns traceable source records into contract-aware, normalized relative-value observations and explainable anomaly outputs, then exposes them to the existing dashboard.
3.2 Goals
Keep the existing React UI visually and behaviourally consistent while moving data and analytics behind versioned APIs.
Preserve original source files; record file hashes, source paths, import attempts and validation results.
Distinguish futures price data from aggregate activity reports, options data, contract specifications and illustrative demo data.
Maintain a canonical contract/pair model and version contract specifications by effective date.
Centralize normalization and anomaly-scoring logic so the frontend does not become a competing source of analytics truth.
Provide traceable data-quality outcomes and explicit statuses: verified, provisional, illustrative or quarantined.
Provide the foundation for walk-forward backtesting without look-ahead leakage or unsupported profit claims.
3.3 Non-goals for the first backend release
No broker integration or real-money order execution.
No prediction guarantee, investment advice or profitability guarantee.
No requirement to replace the frontend design system or redesign the existing pages.
No automatic extraction of legally/economically authoritative contract rules from PDFs without verification.
No forced adoption of a deep-learning model before a simple statistical baseline and data pipeline are validated.
No destructive cleanup or in-place conversion of the uploaded source files.

6. Data policy and current limitations
6.1 Immutable source policy
The existing `GoldMcx_Data - Copy/` folder and separately added BhavCopy files are input assets only.
The backend may read and checksum the files, but may not rename, rewrite, re-save, reformat, delete or move them.
Parsed data, quarantine files, manifests, logs, cache files and exports must live under backend-owned directories or PostgreSQL.
Keep exact relative path, SHA-256 checksum, byte size, detected media format, discovered time, import run and parser version.
6.2 Source classes
Class
 | Use
 | Rule
 | 
Futures Bhavcopy / FUTCOM
 | Potential primary source for expiry-specific OHLC, volume and OI.
 | Eligible only after schema and row-level validation.
 | 
Date-wise Detail report
 | Trade activity/lots and aggregate value.
 | Store in activity tables; do not treat aggregate value per lot as an official closing price.
 | 
Date-wise Summary report
 | Summary-level activity.
 | Separate source class; avoid double-counting with Detail reports.
 | 
OPTFUT / option rows
 | Options-related or option-on-futures data.
 | Do not admit to the four-futures price-series table by symbol name alone.
 | 
Contract-specification PDF
 | Reference for contract and expiry rules.
 | Register and extract for review; authoritative normalized fields require a verified versioned contract master.
 | 
Existing TypeScript demo data
 | Fallback / UI continuity.
 | Keep intact; label as illustrative and never merge silently with verified prices.
 | 

Data-quality status  Every dataset/observation must carry provenance and a quality class: VERIFIED, PROVISIONAL, ILLUSTRATIVE or QUARANTINED. The application must not present a provisional or illustrative price as a verified MCX price.
 | 
7. Key user journeys
7.1 Dashboard load
1. Frontend requests the dashboard summary and data status.
2. Backend returns contract cards, latest validated/eligible signals, source freshness and quality labels.
3. If the API is unavailable, the adapter may use local demo data only when fallback mode is explicitly enabled.
4. UI design and current components remain unchanged.
7.2 Import and validate source files
1. Admin/developer configures the source folder via MCX_DATA_DIR; default expected location is the existing data folder beside the frontend.
2. Importer discovers files and computes checksums without modifying them.
3. Parser sniffs native XLS, HTML-table XLS, CSV and PDF by content/signature as well as extension.
4. Rows are staged, classified and validated; ambiguous/unsupported rows are quarantined with reasons.
5. Import report shows discovered/parsed/accepted/rejected counts and data-quality status.
7.3 Compare contracts and score novelty
1. Frontend selects two canonical contract instruments and, where relevant, explicit expiry contracts.
2. Backend returns normalized series/spread with source and contract-specification version.
3. For the selected pair, backend calibrates only on the allowed historical training window.
4. A held-out/new observation is scored without using itself or future data in calibration.
5. Response explains the score, threshold, calibration window, input quality, expiry and liquidity flags.

10. Risks and mitigations
Risk
 | Impact
 | Mitigation
 | 
Wrong report type imported as futures price
 | False prices and misleading anomalies.
 | Sniff content and instrument type; quarantine options; gate on valid OHLC and expiry.
 | 
Summary/Detail double count
 | Inflated activity metrics.
 | Distinct source classes, row hashes and semantic de-duplication rules.
 | 
Incorrect or stale contract specification
 | Biased normalization.
 | Effective-dated contract master with source document, review status and formula tests.
 | 
Near-month series mixes expiries
 | Artificial spread jumps.
 | Key price rows by symbol + expiry_date + trade_date.
 | 
Legacy pair alias mismatch
 | Comparison/model page returns wrong or missing data.
 | Canonical backend pair IDs and adapter alias mapping; telemetry/log warnings.
 | 
Backtest leakage
 | Optimistic performance.
 | Chronological split, calibration cutoff enforcement and leakage tests.
 | 
Backend integration breaks frontend
 | Screens regress.
 | Feature flag, adapter boundary, existing local mode, screenshot/route smoke tests.
 | 
Original data files changed
 | Data provenance lost.
 | Read-only mount, checksums before/after import and tests asserting no source writes.
 | 

11. Definition of done
Existing frontend source/data files remain present; current pages still build and render.
Original data folder is read-only to the application, with no changed file hashes after ingestion.
Backend starts with documented commands and has health/readiness endpoints.
Ingestion report distinguishes parsed, accepted, rejected and unsupported inputs.
Core tables separate futures prices from activity reports and option rows.
All four symbols and six canonical pairs are handled without silent fallbacks to a different pair.
Normalization and anomaly scoring have automated unit tests.
Score response includes provenance, calibration period, scale fallback and algorithm version.
Frontend can run in local demo mode if backend is unavailable and can switch to API mode by configuration.
Build/test commands, environment variables, data limitations and known gaps are documented.
